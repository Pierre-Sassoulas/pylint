Method

How a verdict on these boards was produced, and the three ways a bisect over this repository will hand you a confident wrong answer.

Reading a verdict

  • reproduces — the reporter's own snippet was rebuilt and still emits the reported message on pylint main, with their library installed at a version that shows it.
  • never repro'd — clean at the exact pylint, astroid and Python named in the report. Nothing was fixed; something in the reporter's environment was doing the work.
  • needs repro / not re-run — the issue points at code that was never public, or carries nothing runnable. Not a judgement on whether the bug is real.
  • fixed upstream — pylint is not the place to fix it, and the row names the version floor.

Pin the reporter's era, not just their pylint

#4577 is clean on pandas 3.x and fires on 1.5.3 and 2.0.3 — the message tracks the library version, not any pylint change. #9311 turned out to be fixed by torch 2.8.0 with pylint untouched, and #8024 by Cython 3.3.0. A library issue that looks stale usually just needs its era pinned back before you believe it.

And read the whole thread: #4577's body snippet is genuinely fixed, but a snippet from the comments still fires. The tell was a comment postdating the fixing commit by three years.

Bisecting

Per step: install pylint (or astroid) from a detached worktree into a venv holding the reporter's library, run the snippet, grep for the reported message. git bisect run with --term-old=buggy --term-new=fixed, so the "first fixed commit" is where the message disappears.

Three traps, each of which produces a confident wrong answer rather than an error:

  1. setuptools build/lib persists across checkouts. A file deleted in a later commit keeps being packaged into every subsequent wheel — symptom: a pylint 3.3.5 install crashing inside pylint/checkers/python3.py, a file removed after 2.5. Purge build/ and *.egg-info in the tree and pylint/ plus pylint-*.dist-info in site-packages before each install.
  2. rc=$? after a pipe captures the last stage. res=$(check.sh ... | head -1); rc=$? always yields head's 0, so every step reports "buggy", the bisect walks forward and converges on the tip.
  3. The astroid pin is a range. An installer that leaves an already-satisfying astroid in place makes each step depend on the previous one. Pin each commit's own CI-tested astroid from requirements_test_min.txt.

Old tags need old toolchains: pylint ≤ 2.6 carries a python_requires modern setuptools rejects; pylint 2.8 wants inspect.formatargspec, gone in 3.11, so py3.10; pylint 2.x imports pkg_resources, so setuptools<81. pylint 1.6.5 and 2.5.0 will not build on any Python available here. #10433 needed a Fedora 43 container for CPython 3.14 plus the real NetworkManager GI typelib — PyGObject has no wheels.

Refreshing the boards

One GraphQL request covers every tracked issue — aliased i<number>:issue(number:…) nodes in a single query — rather than one call per issue. Two contents calls give the astroid pin on main, and one commits call says what landed.
